# PI-Harness 详细会话渲染性能设计

## 背景

打开大型 pi 会话时，现有实现先等待 pi RPC 完成初始化，再调用 `get_messages` 返回完整消息数组，最后在 UI 线程逐条加入 WPF 集合。本机真实样本达到 121.17 MB，其中约 117 MB 是历史工具图片数据；基线中 pi 就绪约 27 秒，`get_messages` 额外传输约 8.2 秒，且逐条集合通知会重复触发布局和自动滚动。

## 目标

- 点击会话后尽快显示可读的当前活动分支历史。
- pi 完整上下文仍在后台正常加载，准备完成后可继续对话。
- 不新增第三方依赖，不修改 pi 会话文件，不丢失用户、助手、思考和工具文字。
- 大会话不再通过 RPC 复制图片 Base64 到 PI-Harness。
- 历史列表只执行一次批量刷新，自动滚动请求需要合并。

## 方案选择

### 采用：本地轻量历史与 pi 后台就绪解耦

PI-Harness 直接顺序读取已有 JSONL，会话项只保留 `id`、`parentId` 和当前界面需要的文字字段。读取完成后从最后活动叶节点沿 `parentId` 回溯，得到当前活动分支。图片内容不解码、不保存、不显示，与现有界面行为一致。

本地历史读取和 pi RPC 初始化并行执行。历史读取完成后立即批量更新右侧界面；pi 完成 `get_state` 后更新模型信息并开放发送。正常路径不再调用 `get_messages`。

### 未采用方案

- 仅批量绑定 RPC 历史：可减少 WPF 抖动，但 121 MB RPC 响应仍存在。
- 分页或 WebView：性能上限更高，但会改变交互并增加实现或运行依赖。

## 组件调整

- `SessionHistoryReader`：容错读取 JSONL、提取轻量消息、还原活动分支。
- `SessionHistoryItem`：Core 层的轻量显示模型，不持有图片数据。
- `BulkObservableCollection`：以单次 Reset 替换全部历史项。
- `MainViewModel`：并行执行本地历史读取与 pi `get_state`，移除正常路径的 `get_messages`。
- `MainWindow`：合并重复的 `ScrollIntoView` 调度，正确解绑 Reset 前的消息事件。

## 错误与并发

- 单行损坏只记录并跳过；文件无法读取时显示明确错误，同时 pi 初始化仍可独立失败或成功。
- 会话切换期间沿用现有状态机，禁止并发切换。
- 本地读取支持取消接口；第一版继续沿用单会话串行切换，不引入多 RPC 客户端。

## 测试与验收

- 当前活动分支回溯，排除废弃分支。
- 图片 Base64 不进入显示模型。
- 用户、助手、思考、工具结果、压缩摘要映射保持正确。
- 损坏 JSONL 行隔离。
- 批量集合仅产生一次 Reset 通知。
- 真实 121.17 MB 会话端到端复测，对比修复前 21.6 秒截图基线及 35.2 秒纯 RPC 基线。
- 既有自动化、真实 pi 流式发送、发布包启动和截图验收全部通过。

## 边界

本次不增加历史搜索、分页按钮、图片预览和分支树编辑。pi 仍必须加载完整上下文后才能继续发送；优化目标是避免右侧详情界面冻结和重复的大数据 RPC 传输，而不是改变 pi 自身的会话初始化成本。
